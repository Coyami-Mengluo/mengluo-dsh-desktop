# Security

This is an unofficial, unsigned Windows preview maintained on a best-effort basis. A passing test or dependency audit is not a complete security review.

## Data and update boundaries

- Client code, Electron and installation tools live in the application directory. Managed Harness versions and client preferences live under the current user's application profile. The first-install page and client settings share `download-settings.json` in that profile; it contains only a fixed download-source identifier. Harness itself owns its home, credentials, plugins and conversations; workspaces live under Windows Documents by default.
- Client updates use only the public `Coyami-MengLuo/mengluo-dsh-desktop` GitHub release feed embedded in the application. No GitHub token is included. HTTPS, GitHub account/release access controls, and the SHA-512 digest in release metadata are the trust basis for unsigned builds. A digest from the same compromised feed cannot authenticate an uncompromised publisher. Enable account 2FA, protect release permissions, and add Windows code signing before making stronger publisher-authentication claims. The application does not disable certificate verification or override the updater's signature verifier.
- Downloads prefer blockmap-based reconstruction of the installer. The updater verifies the completed installer digest before making it installable. Download or metadata errors do not authorize installation. Installation requires an explicit restart confirmation, and Harness shutdown must finish first. This is not a claim of atomic rollback after power loss during NSIS installation.
- Automatic **client** checking does not download or execute client updates automatically. Normal quit does not install them. Portable/development clients do not self-replace. The client refuses downgrade/prerelease metadata and unexpected installer filenames. Harness automatic checking is separate: it can download, verify and run an isolated startup check for a candidate in the background, then requires restart confirmation before switching the active version.
- The official UI has no shell preload bridge. The separate local shell, update and settings pages use a sandbox, context isolation and restrictive content policies. Settings and update actions accept only exact local main-frame senders and fixed operations. The settings renderer cannot supply arbitrary commands, filesystem paths, URLs or download registries; its preferences accept only allowlisted fields and values.

## Harness mirror boundary

Official npm is the default. The only alternate managed-package source is the third-party `https://registry.npmmirror.com/` service; it is not an official DeepSeek or npm service. Source selection affects future managed Harness npm installation/update tasks only. It does not alter global npm configuration, terminal npm settings, Git plugin downloads, the fixed GitHub client-update feed, or the pinned Node toolchain's distribution source.

For mirror installs, official npm still determines the exact Harness version, complete dependency graph and SHA-512 integrity values. The mirror transports package files for that verified lock; it cannot select another graph or substitute a newer/older version. The client checks that the manifest and official lock remain unchanged. npm still verifies the downloaded package integrity, and normal runtime verification and startup checks remain required before activation.

Only recognized mirror transport failures, such as connection errors or missing files, permit a retry against official npm using the same lock and remaining timeout budget. A changed graph, missing verification information or integrity failure does not authorize weaker checks, arbitrary sources or activation of the candidate. If official metadata is unavailable, choosing the mirror does not bypass that requirement. HTTPS and official-registry metadata remain trust dependencies; a checksum from a compromised authoritative source does not establish independent publisher authenticity.

## Plugin boundary

The plugin store is a read-only discovery surface over public, non-archived, non-fork GitHub repositories carrying the `dsh-plugin` topic. Keywords use GitHub's remote repository search across names, descriptions and READMEs. Each page contains at most 100 entries; further pages load only on request, up to GitHub's 1,000-result search limit. Incomplete results and the search limit are shown rather than presented as an exhaustive inventory; repositories without the topic are outside this scope. Query changes cancel or disregard stale responses, and debounce plus a bounded cache reduces repeated anonymous requests. Topic membership and static bundle declarations are not approval, ownership verification, a security audit or a guarantee of compatibility. Third-party metadata is untrusted display data, never a source of shell commands. Repository authors, dependencies and install behavior must be reviewed by the user before installation; third-party plugins can execute code with the permissions available to Harness.

Entering the plugin page and update checks perform metadata reads, not plugin installation or background automatic updates. Mutating actions require an explicit user action and confirmation and invoke the selected runtime's official Harness plugin CLI. Targets are pinned npm versions or GitHub commits, not commands supplied by the renderer or copied from a third-party README. These controls manage user-added plugins in the `web` profile, not official built-in components. The client serializes plugin changes with its own Harness update operations. It cannot coordinate unrelated external processes: do not modify that same profile concurrently through a terminal or the official UI. A timeout or cancellation is not a guarantee that the official CLI made no partial changes; inspect the installed list before retrying.

The client's `plugin-sources.json` stores only minimal origin bookkeeping (package/spec, public repository, tracking ref and exact commit) in the application profile. It contains no tokens or other credentials and is separate from official plugin configuration. Origin records are used only when they match the current installed source. Unknown or unsupported origins, and old GitHub branch installs without a reliable installed commit or tracking ref, do not authorize an inferred update. GitHub plugins first installed through the store retain their chosen tracking ref and pinned commit for later read-only comparison. Publisher compatibility declarations are informational, not independently tested compatibility claims.

Metadata requests use the system proxy, are credential-free and are confined to fixed HTTPS GitHub API and official npm origins, with response-size limits, timeouts, cancellation and no redirects. They disclose search keywords and the relevant public repository or npm package name to those services, not conversations or plugin configuration. Do not enter secrets in the store's search box. Network providers still receive normal connection metadata, and GitHub's anonymous API limits may delay searches and checks; caching and debounce do not remove these limits. Plugin downloads follow the system proxy and the official package tooling's behavior. The Harness mirror selector does not change plugin registries or global npm configuration. Recent CLI output is bounded in the settings page; never post complete diagnostics publicly without reviewing them for private paths, credentials or other sensitive content.

## Reporting

Before the repository is published, contact the maintainer through an already established private channel. After publication, use GitHub's private vulnerability reporting feature **only if the repository owner has enabled it**. Do not post secrets, exploit details involving personal data, complete logs or conversations publicly. General non-sensitive defects may be reported as issues.

## Before publishing

Run `npm run check:release`. It checks the allowlisted source tree for common secret patterns and personal absolute paths, but is not a full credential or dependency-code audit. The original private repository and its Git history are not part of this standalone export and have not been approved for publication. Review every added file and any diagnostic attachment separately.
